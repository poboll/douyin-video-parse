# 02 · 抖音精选（AwemeJX）视频解析

> App：抖音精选，bundle `com.ss.iphone.yumme.video`
> 核心二进制：`AwemeJXCore.framework/AwemeJXCore`（arm64 单片 922MB，含符号）
> 目标案例：《女主》第二集，69.7 分钟，itemID `7642311481656184074`

---

## 1. 整体路线图

```
① 摸清缓存结构        .mdl = 裸 MP4，.mdlnodeconf = ttmd 索引
② 找 gear 模型        清晰度档位表，确认离线下载为什么只有 576p
③ 拿播放直链          api-play dash → er=0 无水印链（普通视频）
④ 缓存逆向失败        播放器只预下载音频轨，视频走流式不落盘
⑤ 注入抓流            hook VTDecompressionSessionDecodeFrame 抓明文码流
⑥ 重封装出片          HVCC → Annex B → ffmpeg -c copy
```

前四步走了一整天，第五步才是正解。**教训：先验证"内容是否加密"，再决定要不要走解密路线**——见 [03](03-加密研究完整复盘.md)。

## 2. 缓存结构

### 2.1 目录布局

```
Library/Caches/
├── TTPlayerCache/               ← 播放缓存（AVMDL）
│   ├── <fkey>.mdl               ← 数据，裸 MP4（ftyp 头）
│   └── <fkey>.mdlnodeconf       ← ttmd 魔数二进制索引，仅区间表 + fkey，无 URL
├── offlineCaches/               ← 离线下载缓存
├── offlineCenter/
├── JingXianFeedCache/
├── feedPrecacheV2/
└── mdlManual/

Library/AWEStorage/FilePermanent/AWEOfflineVideoCenter/<uid>/<n>/kAWEOfflineCenterModelKey
    ← NSKeyedArchiver bplist，含 downloadedModels（title / itemID / fileSize / isFileExist）
```

### 2.2 关键事实

- **`.mdl` 就是裸 MP4**，`ftyp` 开头，`ffprobe` 能直接读
- **`.mdlnodeconf` 里没有 URL**，只有区间表和 `fkey`（md5）。`fkey` 只是缓存 key，**不是密钥**（这点一开始搞错了）
- **视频 / 音频分轨存储**（DASH）：视频一个 `.mdl`，音频另一个 `.mdl`
- 文件名带 gear 名，直接告诉你是谁：`v0200fg1..._bytevc1_1440p_2040416.mdl`
- 缓存文件是**预分配稀疏**的：没下载的区间是零填充，别把文件大小当成已下载量

### 2.3 两套缓存路径的区别（重要）

| | AWEOfflineCenter（离线下载） | TTPlayerCache / AVMDL（播放缓存） |
|---|---|---|
| 触发方式 | 点「缓存 / 下载」按钮 | 播放 |
| 清晰度 | **低档**（576p / 684kbps） | **高档**（实测摸到过 1440p、4K 残片） |
| 完整性 | 会填满 | 稀疏，只下播过的部分 |

**这就是"离线下载很糊"的根因**：不是网络问题，是 App 产品策略——离线下载走独立的一套，自己选了最低档。播放缓存才上得去高画质。

## 3. gear 模型（清晰度档位表）

从 `AwemeJXCore` 里挖出的播放模型结构：

```
每档画质:
  gear_name          # 档位名
  quality_type       # 质量类型
  bit_rate           # 码率
  play_addr          # H.264 直链
  play_addr_265      # H.265 直链
  is_bytevc1         # 是否字节自研 VC1（HEVC）

档位表:
  gear_group
  default_gear_name
  bitrateRange
  minNetwork         # 最低网络要求
```

播放时按 `minNetwork` 自适应选档。**想拿最高画质，必须在 App 里手动切档**——自动选择会摸到中档。

## 4. 为什么最终走了注入抓流

按 2.3 的思路，本来打算"让 App 完整播放一遍 → 缓存填满 → 拷出 `.mdl` → 重封装"。实测失败：

- 音频缓存 `c98cb35.mdl` 69.9MB **完整写完**（23:58 写完）
- 视频缓存 `dcb282cc.mdl` 790MB **覆盖率只有 2.9%**（mtime 停在 23:52 不动）
- 中间 760MB 全是零

**根因：该播放器只预下载音频轨，视频走流式解码不落盘。**

旁路也排查干净了：TTPlayerCache 只有那个稀疏文件，`hlsproxy_default_file_dir` / 容器 `/tmp` 全空——**没有第二条捷径**。

## 5. 注入抓流（正解）

### 5.1 抓取点选择

主二进制导入表核实：

- `VTDecompressionSessionDecodeFrame` ✓（off 687461868）
- `VTDecompressionSessionDecodeFrameWithOutputHandler` ✗（没有这个变体）
- `CMBlockBufferGetDataLength` / `CMBlockBufferCopyDataBytes` / `CMSampleBufferGetDataBuffer` ✓

→ hook `VTDecompressionSessionDecodeFrame`，按会话把 `CMSampleBuffer` 的 block buffer 追加写盘。

### 5.2 产物格式

```
Documents/ep2dump/frames/sess_<ptr>.h265    # HVCC，4 字节长度前缀
Documents/ep2dump/frames/sess_<ptr>.idx     # 每行 offset size pts
```

文件头 `0000001d 40010c02` = 长度 29 + VPS → **明文 HEVC** ✓

### 5.3 重封装（关键坑）

```bash
# 必须把 4 字节长度前缀换成 Annex B 起始码 00 00 00 01
# 否则 ffmpeg 把 00 00 00 1d 当垃圾吞掉 → 全程 "PPS id out of range" → 一帧都解不出
cat ps.h265 sess_X.h265 > all.h265
ffmpeg -f hevc -i all.h265 -c copy -movflags +faststart out.mp4
```

参数集（VPS+SPS+PPS，共 126 字节，类型 `[32,33,34]`）从缓存文件头提取，拼接时放在最前面。

### 5.4 已知缺陷

`CMSampleBufferGetPresentationTimeStamp` 返回 invalid CMTime（App 建的 sample buffer 无 timing info）→ idx 里 pts 全 -1。

**替代校验**：GOP 边界分析（每 GOP ≈ 3MB / 398 帧）+ 字节模式去重。

## 6. 注入路线演进（v1 → v17）

每一版都是上一版实测失败后的修正，完整动机见各条：

| 版本 | 手段 | 结果 |
|---|---|---|
| v1 | ObjC swizzle `MediaDecrypter` 14 个 selector | 装上但零调用 |
| v2 | fishhook native 层 | **闪退**（符号表被 `radr://5614542` 假条目混淆） |
| v3 | 按值扫描指针槽 | 绕过假符号表，但仍闪退 |
| v4 | SIGSEGV 保护 + app-bundle-only 过滤 | **定位闪退根因 = 启动期 dyld API 竞争**，非补丁本身 |
| v5 | 错峰下补丁 | 稳定，日志确认状态 |
| v6 | 故障保护版 | 插件完全就绪，等播放触发 |
| v7 | 立即补丁 + AES 数据面（boringssl 10 个符号） | **零调用** |
| v8 | + `av_aes_gcm_256_decrypt`（自研 AES-256-GCM） | 仍零调用 → **引出"根本没加密"的怀疑** |
| v9 | 改 hook `VTDecompressionSessionDecodeFrame` | 抓到明文码流，路线成立 |
| v10–v12 | 完善抓流 + 试抓音频（AudioQueue / AudioUnit） | 视频成功；音频零调用 |
| v13–v15 | 改试 `AVAudioPCMBuffer` / `AVAudioNode` tap | 全部零调用，App 不走这条 |
| v16 | 全家桶：`avcodec_receive_frame` + AudioConverter + AudioUnit + dlsym 拦截 | **`avcodec_receive_frame` 中招** ✓ |
| v17 | 补开头几秒 + 视频 dump 重开 | 片头仍缺（App 断点续播，见下） |

### 6.1 符号表混淆（v2 的坑）

`AwemeJXCore` 的符号表里大量 `radr://5614542` 形式的**假条目**，真实绑定在自研节 `__bd_la_sym_ptr`。所以 fishhook 按符号名 hook 会失败，必须**按值扫描指针槽**。

### 6.2 闪退根因（v4 的教训）

一开始以为闪退是补丁打错了。实测发现是**启动期 dyld API 竞争**——constructor 里调 dyld 相关 API 会和 dyld 自己抢锁。修法是错峰 + SIGSEGV 保护 + 只过滤 app-bundle 内的槽。

### 6.3 音频为什么难抓（v12–v16 的弯路）

依次试过，全部零调用：

- `AudioQueueEnqueueBuffer` / `AudioQueueNewOutput` —— 不走
- `AudioUnitRender` / `AudioUnitInitialize` —— 只调过 1 次，且是 byteaudio/RTCLive 的槽，非播放路径
- `AVAudioPCMBuffer` 的 `floatChannelData` / `int16ChannelData` getter —— 不走
- `AVAudioNode` 的 `installTapOnBus:bufferSize:format:block:` —— **注：这个方法在新版 SDK 里从 AVAudioEngine 挪到了 AVAudioNode**，v14 因此白跑一轮；且 App 根本不调

镜像清单显示 App bundle 内有 `AudioXAAC.framework`（字节音频引擎）+ `TTFFmpeg.framework` + `byteaudio.framework` → 音频大概率走 FFmpeg 解码。

**最终命中 `avcodec_receive_frame`**：`sample_fmt=8(FLTP) ch=2 nb=1024` → 交织 float32 落盘。

> 这是**解码点**抓取（解码后、输出前），所以即使 App 按 3 倍速播放，抓到的内容依然完整原速——不需要倍速还原。

## 7. 断点续播的坑（片头为什么抓不到）

三轮抓取，音频全部从 ~6.6s 起，始终拿不到 0–6.6s 的真片头。

**破案**：dylib 只 hook 解码，日志里没有任何 seek 记录。但 dump 数据证实是 **App 断点续播**——续播会话首帧与上一轮第 19 帧字节级相同（md5 `a7fcc229...`）。每轮播放都从上次观看位置 ~6.667s 恢复，所以片头从未被解码、更没被 dump。

起播点随拖动位置变化（上轮 6.62s，这轮 5.785s）——App 就是不给 0–5.8s。

## 8. 免认证 WebDAV 暴露（安全提醒）

iPad 上某个 App 的 WebDAV 服务（`192.168.1.70:11111`）**免认证暴露了整个 iPad 文件系统**，不只是 App 容器——相册、微信数据库全在里面。

本次分析大量依赖它读沙盒，但**事办完必须关掉**。同一 WiFi 下谁能读你整个设备。

PROPFIND 有两个坑：

1. **目录也返回 `getcontentlength`**——判断目录必须看 `resourcetype/<D:collection/>`，只看长度会把目录当文件
2. `<D:getcontentlength>` 和 `<D:href>` 之间隔着 `resourcetype` / `displayname` 等元素，**正则需要容错，不能要求相邻**
