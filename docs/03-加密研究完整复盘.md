# 03 · 加密研究完整复盘

> 这是本仓库**最该看的一篇**。
> 它记录了一次彻底的误判如何被推翻，以及为什么最终结论是「**视频根本没加密**」。
> 如果你只从这篇里学一件事：**熵值不能当加密证据。**

---

## 1. 结论先行

**抖音（含抖音精选付费版权内容）的视频载荷没有加密。**

- 缓存 `.mdl` 是标准 fMP4：`ftyp isom` + `moov` + `sidx` + `moof` + `mdat`
- mdat 负载开头：`0000001d 40010c02…` = 长度 29 + VPS；`0000004e 420103…` = 长度 78 + SPS
- NAL 链 `[32,33,34,39,19]` = VPS / SPS / PPS / SEI / IDR，**纯明文**
- `ffprobe` 直接读通：`hevc 2560x1440, duration 4181.35s`

抖音的版权保护是**链路准入 + 水印 + 缓存策略**，不是 DRM。详见 [README Q3](../README.md#q3为什么-api-接口是投毒的现在-app-获取的却是未加密的)。

---

## 2. 时间线：一次彻底的误判

### 阶段一：误判「DRM 加密」

起因：从 App 实际使用的直链下载文件，抽帧全绿；moov 能读，mdat 载荷"看起来"高熵。

当时下的结论：

> 付费合集内容（如《女主》第二集）在 api-play dash / api.amemv.com / iesdouyin / douyin.com web **全部 404** —— 服务端按视频 ID 封锁明文路；app 自用的 `er=1` 直链可下载但 mdat 加密，缓存 `.mdl` 同样加密。

据此立项：**逆向解密流程，拿密钥。**

### 阶段二：定位解密实现（方向看起来对）

从 `AwemeJXCore` 挖出 `_OBJC_CLASS_$_MediaDecrypter`：

```
decryptBlock:
aesDecryptCacheData:withKey:error:cost:
aesDecryptwithData:KeyData:keySize:ivData:
AESDecryptData:keyData:ivData:
buildEncryptedDecryptionKey:
```

确认解密是 AES（CBC/GCM 变体）。然后进一步挖到 TTFFmpeg 里的自研函数：

```
av_aes_gcm_256_decrypt @0x193438
  int av_aes_gcm_256_decrypt(out, outLen, in, inLen, ?, key, iv, ivLen, tag)
  内部: EVP_aes_256_gcm → ctrl(SET_IVLEN) → EVP_DecryptInit_ex(ctx,NULL,NULL,key,iv)
        → 分块解密 → SET_TAG
```

主二进制导入了这个符号，GOT 槽可被按值扫描抓到。**看起来证据链完整。**

### 阶段三：hook 全部零调用（第一次警报）

v7 下了 10 个 boringssl hook（`AES_cbc_encrypt` / `AES_ctr128_encrypt` 等）→ **播放时全部零调用**。
v8 加到 14 个，含 `av_aes_gcm_256_decrypt` 本体 → **仍然零调用**。

当时的解释："解密不走 boringssl，走自研实现"——然后去逆向 `av_aes_gcm_256_decrypt`，越挖越深。

### 阶段四：一锤定音（误判推翻）

直接解析 mdat 里的 NAL 结构，不再看熵值：

```
0000001d 40010c02…   ← 长度29 + VPS(NAL type 32)
0000004e 420103…     ← 长度78 + SPS(NAL type 33)
NAL 链 [32,33,34,39,19] = VPS/SPS/PPS/SEI/IDR
```

**完整可解析的 HEVC 参数集 + IDR。如果是加密数据，不可能出现合法的 NAL 头序列。**

`ffprobe` 直接读通 → **根本没有加密。**

---

## 3. 误判的根因

**用「熵 8.0」当加密证据。**

```
实测：目标文件 mdat 熵 = 8.00
      已知可用的 2.5GB 文件 mdat 熵 = 8.00
      → 两者一样，判据无效
```

**压缩视频的熵本来就是 8.0 左右。** 已经压缩过的数据看起来和随机数据一样——这是压缩的本质，不是加密的特征。

这个错误判据导致：

- 白丢了 6GB"加密废文件"
- v7/v8 两轮注入白做
- 逆向 `av_aes_gcm_256_decrypt` 的深度工作完全用在了不存在的问题上
- **更糟的是**：它让我们一直往"拿密钥"这个错误方向走，而正解（hook VT 解码入口抓明文码流）从一开始就是打开的

### 正确的判据（按可靠性排序）

| 方法 | 可靠性 | 说明 |
|---|---|---|
| **解 NAL 结构** | ⭐ 决定性 | 能解出合法 VPS/SPS/PPS/IDR 就是明文，没有例外 |
| ffprobe 能否读通 | ⭐ 高 | 同上，且更快 |
| 搜明文参数集头 | 高 | `00 00 00 01 40 01 0c`（HEVC）等 |
| 熵值 | ❌ **无效** | 压缩视频熵也是 8.0 |

---

## 4. 那"投毒"到底是什么意思

既然载荷是明文的，"api 接口投毒"投的是什么？

**投在准入层，不在载荷层。** 三件套：

### 4.1 链路准入（对外的部分）

四个端点对目标视频全部 404：

- `api-play.amemv.com/aweme/v1/play/dash/`
- `api.amemv.com/aweme/v1/play/dash/`
- `www.iesdouyin.com/aweme/v1/play/`
- `douyin.com` 网页端

带全设备参数也 404。**这不是"加密了不给你解"，是"不让你问"。**

### 4.2 水印（对搜索流量的部分）

`lr=aweme_search_suffix` 的链会多渲染一路带抖音号的版本，水印**烧录在画面像素里**。给你能用的东西，但是残次品。

### 4.3 缓存策略（对离线下载的部分）

- 离线下载走 `AWEOfflineCenter`，只给 576p / 684kbps
- 播放才给高档（1440p / 4K）
- 播放器**只预下载音频轨，视频走流式不落盘**

三层都是产品与策略，没有一层是密码学。

### 4.4 App 为什么拿到明文

因为 App 本来就是明文链的合法请求方。它用 `api-play.amemv.com/aweme/v1/play/?video_id=..&biz_sign=<blob>` 这条带设备签名的换档服务，服务端返 `er=0` 干净链，VideoToolbox 直接解，**中间没有任何解密步骤**。

这正是 14 个 AES hook 零调用的原因——**不是 hook 失败，是本来就没有东西要解密。**

---

## 5. 404 的根因（未完全定案）

诚实说明：**最终没有完全定案。**

两种可能都没排除：

1. **签名不新鲜**：dash 端点要 `file_id` + `sign`，我们手里的可能是旧的
2. **服务端按视频策略封锁**：该内容确实对外部请求关停了明文路

**但可以确定它不是 DRM**——因为同一部视频 App 侧拿到的是明文码流，最终从 `VTDecompressionSessionDecodeFrame` 解码入口完整抓出 790MB 并成功出片。

> 方法论教训：**"我拿不到"不等于"它被加密了"。** 拿不到可能只是你的请求不对。先证明载荷的性质，再解释为什么拿不到。

---

## 6. 最终采用的技术方案

既然内容是明文，就不需要密钥，只需要**在解密发生前的那一点把明文拿出来**。

播放器不落视频缓存 → 改从 VideoToolbox 解码入口抓：

```objc
// hook VTDecompressionSessionDecodeFrame
// 按会话把 CMSampleBuffer 的 block buffer 追加写盘
// 产物: Documents/ep2dump/frames/sess_<ptr>.h265 (HVCC 4字节长度前缀)
```

重封装：

```bash
# 必须把 4 字节长度前缀换成 Annex B 起始码
cat ps.h265 sess_X.h265 > all.h265
ffmpeg -f hevc -i all.h265 -c copy -movflags +faststart out.mp4
```

**踩坑**：拼接参数集时必须用 Annex B 起始码 `00 00 00 01`，保留 4 字节长度前缀的话 ffmpeg 会把 `00 00 00 1d` 当垃圾吞掉 → 全程 `PPS id out of range` → 一帧都解不出。

## 7. 音频抓取的弯路（顺带记录）

视频抓到了，音频另有一场弯路。依次试过、全部零调用：

| 目标 | 结果 |
|---|---|
| `AudioQueueEnqueueBuffer` / `AudioQueueNewOutput` | 零调用 |
| `AudioUnitRender` / `AudioUnitInitialize` | 只 1 次，非播放路径 |
| `AVAudioPCMBuffer` 的 `floatChannelData` / `int16ChannelData` | 零调用 |
| `AVAudioNode` 的 `installTapOnBus:...` | 零调用 |

两个副教训：

1. **`installTapOnBus:bufferSize:format:block:` 在新版 SDK 里从 `AVAudioEngine` 挪到了 `AVAudioNode`**——v14 hook 错了类，白跑一轮。hook 前先用 `class_copyMethodList` 核实方法到底在哪个类上。
2. 镜像清单（`AudioXAAC.framework` / `TTFFmpeg.framework` / `byteaudio.framework`）早就提示音频走 FFmpeg 解码——**早该从导入表反推，而不是逐个 API 试**。

最终命中 **`avcodec_receive_frame`**：`sample_fmt=8(FLTP) ch=2 nb=1024` → 交织 float32 落盘。

> 这是**解码点**抓取（解码后、输出前），所以即使 App 按 3 倍速播放，抓到的内容依然完整原速——不需要倍速还原。

---

## 8. 可迁移的结论

1. **熵值不是加密证据。** 压缩视频熵也是 8.0。要判加密，解结构。
2. **"拿不到"≠"被加密了"。** 先证明载荷性质，再解释为什么拿不到。
3. **hook 零调用可能是正确结果。** 它意味着"这条路没有调用"，不是"hook 没装上"。v8 的 14 个零调用其实是答案，当时却当成了失败。
4. **内容不加密 ≠ 没有版权保护。** 准入、水印、缓存策略三件套足以达到商业目的，且比 DRM 便宜得多。
5. **先读导入表再定 hook 点。** 音频那场弯路，导入表一开始就写着答案。
